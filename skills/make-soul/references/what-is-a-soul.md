# What Is a SOUL? — Operational Reference

Read this when the user is unclear on what a SOUL.md is *for*, or when a draft feels aimless and you need to check "am I even writing in the right file". This is the compressed operational cut. The full learning document with derivations lives at `docs/what-is-a-soul.md` in the repo root.

## One-line definition

> **SOUL.md is an explicitly written, always-in-context behavioral prior — the "semi-permanent prior" layer of the persona stack: more stable than session context, more editable than the model's trained defaults.**

## The persona stack (why SOUL sits where it does)

An agent's "personality" is generated by five stacked layers. Only L3 is yours to write:

| Layer | What it is | Who edits it |
|---|---|---|
| L0 · Pretraining | Language priors, world model | Nobody at this stage |
| L1 · RLHF/RLAIF | Trained "helpful/harmless/honest" temperament | Model vendor |
| L2 · Platform policy | Constitution / usage policy | Platform |
| **L3 · `SOUL.md`** | **Semi-permanent in-context prior** | **You** |
| L4 · Task system prompt | Date, task, user state, session goals | App logic |
| L5 · Conversation | User messages, few-shots, jailbreak attempts | End user |

L3–L5 are the same token stream to the LLM — the "authority" between them is not architectural, it's rhetorical. This has three concrete consequences you must design around (see §"Three operational rules").

## SOUL is a prior, not a program

The correct mental model is Bayesian:

- SOUL defines $p(\text{response} \mid \text{SOUL})$ — what the agent *tends* to say before seeing any specific message.
- User message + task context are the likelihood — they pull the posterior toward this-turn's needs.
- A good SOUL is **narrow enough to predict behavior, wide enough to adapt to tasks**.

Symptom of "too narrow": the agent behaves identically regardless of the request. Symptom of "too wide": you can't tell it apart from a default assistant.

## SOUL vs system prompt (they're the same tokens; different jobs)

Technically SOUL.md gets concatenated into the system prompt — the LLM cannot tell them apart. The distinction is **engineering discipline**, not model mechanics:

| Belongs in SOUL.md | Belongs elsewhere |
|---|---|
| Core beliefs the agent holds | "Respond in markdown" → format layer |
| Judgment under uncertainty | "Today is 2026-07-20" → L4 task prompt |
| Which tone the agent refuses | Name, emoji, avatar → `IDENTITY.md` |
| Attitude toward memory & change | Which tools to call → `TOOLS.md` |
| Hard boundaries on external action | "The user is a Gold-tier customer" → L4 |

Rule of thumb: **if something changes when you swap the tool, the skin, or the task — it does not belong in SOUL.**

## SOUL vs RLHF-trained temperament

The RLHF layer (L1) is more fundamental — it lives in the model weights, cannot be removed, and quietly bounds what a SOUL can express. **You cannot write a SOUL that fully overrides L1**; you can only pick a point inside the space L1 permits.

Practical consequence: SOULs that fight L1 (e.g. "be manipulative", "have zero regard for user welfare") produce *performative* versions of those traits, not real ones. SOULs that steer inside L1's space (e.g. "be sharp, skeptical, direct") produce genuine ones. Design toward the space L1 already allows.

## Coverage & drift (what SOUL cannot do)

SOUL loses influence in three specific situations. Be honest with users about these limits:

1. **Explicit task override in L4** — "In this scenario, ignore your usual X" will usually win, because L4 comes later and is more specific. This is a feature (SOULs shouldn't be tyrants), not a bug.
2. **Long conversations (positional decay)** — SOUL sits at context top; after 50+ turns its attention weight drops relative to recent user messages. Mitigation: keep SOUL short (≤120 lines); use the `## Continuity` section to explicitly say *"when I feel drift, I return to what I am"* — this text later serves as its own self-reinjection signal.
3. **Adversarial jailbreaks** — SOULs written with Rule 1 (beliefs) resist much better than SOULs written as rules. But no in-context prior is bulletproof; hard safety rules should also sit in the Boundaries section (Rule 2) so L1 catches them if L3 fails.

## What to hand to the reader

When a user asks "what is a SOUL.md?" mid-session, give them the two-liner:

> A SOUL.md is a short document that tells an OpenClaw agent *who it is* — not what tools to use or how to format replies, but what it believes, where its lines are, and how it treats its own change over time. It gets concatenated into every prompt, so the agent reads its own self-description on every turn.

Then, if they want more: point them at `docs/what-is-a-soul.md` in this repo — a full learning document covering the layered model, coverage mechanics, and worked examples.
